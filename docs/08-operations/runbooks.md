# Operations runbooks

For the technical administrator. Each runbook covers: symptoms → checks → fix → escalate. Background: [railway-deployment.md](railway-deployment.md), [backup-recovery.md](backup-recovery.md), [monitoring-maintenance.md](monitoring-maintenance.md).

**Ground rules**
- Never paste variable values (passwords, keys, tokens, connection strings) into tickets, chats or logs. Refer to variables by name only.
- Production changes, database restores and paid plan changes need the owner's approval.
- Migrations only move forward. Never edit an applied migration; the checksum check refuses changed files.
- Every action in the app is audited. Administration screens: **Backups**, **Audit log**, **Settings → System health** widget.

**Services:** `@hrms/web` (API + web, health `/api/v1/health/live` and `/api/v1/health/ready`), `@hrms/api` worker (background jobs), PostgreSQL (Railway, EU).

---

## RB-01 Deploy failed

**Symptoms:** Railway shows the deployment as failed; the previous version keeps running (Railway only switches when the new one is healthy).

**Checks**
1. Railway → service → Deployments → the failed one → *Build logs* (compile/test step) or *Deploy logs* (pre-deploy migration or start-up).
2. A start-up configuration error names the missing or invalid variable (for example `SESSION_SECRET` too short). Check it exists in the service variables. Do not print the value.

**Fix**
- Build error: fix in a branch, run `npm run lint`, `npm run typecheck`, `npm test`, then merge to `main`.
- Variable error: correct the variable in Railway and redeploy.
- To go back to the previous version: Deployments → previous successful one → *Redeploy*. Allowed only when no newer migration has been applied. Migrations are additive, so older code normally keeps working.

**Escalate:** if the database migration failed, go to RB-02.

## RB-02 Migration failed (pre-deploy)

**Symptoms:** deploy log shows `migrate` error; the new version does not start.

**Checks**
1. Read the error: SQL error in migration `00NN_…`, or `checksum mismatch`.
2. Each migration runs in its own transaction. A failed migration leaves the database unchanged.

**Fix**
- SQL error: write the fix as a **new** migration in a branch, test it against a copy (local test suite runs every migration on a fresh database), and redeploy.
- Checksum mismatch: someone edited an applied migration. Restore the original file from git (`git log -- apps/api/migrations/<file>`) and add the change as a new migration.
- Never delete rows from `schema_migration` by hand.

## RB-03 Site down or slow

**Checks**
1. `GET /api/v1/health/live` checks the process; `GET /api/v1/health/ready` checks the database.
2. Railway metrics: CPU, memory, restarts. Railway PostgreSQL: disk usage and connections.
3. Logs: look for repeated 5xx with the same `requestId`.

**Fix**
- Memory restarts: increase the service memory (needs owner approval if the plan changes).
- Database not ready: see RB-04.
- Many 429 responses: the login rate limiter is working. Check the **Audit log** for `auth.login_failed` from one address.

## RB-04 Database full or unavailable

**Checks:** Railway → PostgreSQL → disk usage; the Backups screen shows the last success.

**Fix**
- Old report outputs and expired sessions are cleaned daily. Check that the worker runs (RB-07).
- Increase the volume (owner approval).
- If the database is lost or damaged: RB-09 restore.

## RB-05 Attendance punches refused

**Symptoms:** employees see *Not on an authorised company network*, or the device check fails.

**Checks**
1. **Attendance setup → Authorised networks.** Is the office's public IP or range listed? The employee's screen shows the address the system sees.
2. If everyone shows the same address (Railway's): `TRUST_PROXY` must be `2` (DL-035).
3. Device check: the employee must register the device first (**Attendance → My attendance devices**). A new phone or browser needs a new registration. HR can revoke old devices.
4. Office IP changed (new internet line): update the network list.

**Fix:** correct the network list, or ask HR to add a correction punch (audited) for the affected days.

## RB-06 Push notifications not delivered

**Checks**
1. The notification keys (VAPID) are generated by the app on first use and stored encrypted; nothing to configure. If the data-encryption key was rotated without carrying the old key (`DATA_ENCRYPTION_OLD_KEYS`), users must turn notifications off and on again.
2. The user allowed notifications in the browser. On iPhone, the app must be added to the home screen.
3. Only the browsers' push services are accepted (Google, Mozilla, Apple, Microsoft). Subscriptions to other addresses are ignored by design.
4. Notifications always remain in the in-app notification centre, even when push fails.

## RB-07 Background job stuck or failing

**Jobs (worker):** absence detection, leave accrual, contract alerts, scheduled reports (hourly), report pruning (daily), backups, off-site sync, audit chain check.

**Checks**
1. The **System health** widget and the Backups screen show the last run of each job.
2. Worker service logs in Railway. Job errors are also sent as notifications to system administrators.

**Fix:** restart the worker service in Railway. Jobs are safe to repeat: they skip work already done.

## RB-08 Account locked or MFA lost

- **Locked account (5 failed attempts by default, Settings → security):** the lock expires automatically after 15 minutes. An administrator can unlock it in **Users → user → Unlock**.
- **Lost MFA device:** an administrator resets MFA in **Users → user → Reset MFA**. The user enrols again at the next sign-in. The action is audited.
- **Last administrator locked out:** use the start-up variables `BOOTSTRAP_ADMIN_*` only on an empty database. Otherwise, a second administrator must help. Keep at least two active administrators.

## RB-09 Restore data

Full procedure: [backup-recovery.md](backup-recovery.md). Summary:

1. **In-app restore (preferred):** **Backups** → choose a backup → *Preview* → confirm with MFA. A second administrator approves. A safety backup is taken first, and the audit log is carried forward. *Undo* is available.
2. **Disaster (database lost):**
   1. Create a new PostgreSQL in Railway (owner approval).
   2. Download the latest encrypted backup from the off-site bucket.
   3. Decrypt it with `node dist/cli.js backup:decrypt <in> <out>`. This needs `BACKUP_ENCRYPTION_KEY` from the owner's safe copy.
   4. Run `pg_restore --no-owner --dbname <new db> <out>`.
   5. Point `DATABASE_URL` to the new database and redeploy.
   6. Verify the audit chain in **Audit log**.
3. Record the time taken (RTO) and the age of the restored data (RPO) in the restore log.

**Keys:** without `DATA_ENCRYPTION_KEY` (encrypted fields) and `BACKUP_ENCRYPTION_KEY` (backups), the data cannot be read. The owner keeps an offline copy of both. Rotation is described in [backup-recovery.md](backup-recovery.md).

## RB-10 Suspected security incident

1. **Contain:**
   - disable the affected accounts (**Users**) and end their sessions;
   - if a key or password leaked, rotate it in Railway (session secret: everyone signs in again).
2. **Investigate:**
   - **Audit log**: filter by user, company, action and date;
   - the chain check shows whether records were changed.
3. **Notify:** the owner decides on GDPR notification (72 hours to the authority when personal data is affected).
4. **Record:** add an entry to the incident log, with the cause and the fix.

## RB-11 Owner routine (monthly / quarterly)

| When | Task |
|---|---|
| Monthly | Review holders of sensitive permissions (salaries, identity documents, restore); review `employee.account_linked` events (residual risk R1); check the Backups screen; check Railway costs |
| Quarterly | Restore drill (RB-09) on a copy, with RTO/RPO recorded; access review; check that the offline key copies are readable |
| Yearly | Public holidays for the new year; leave year-end check; security review |
